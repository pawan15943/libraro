# Library Permissions Reference — `GET /api/v1/app/permissions`

Audience: frontend/mobile developers consuming the Libraro app API. This document explains what the permissions endpoint returns, how each permission key is actually used (or not used) by the backend, and several data quirks in the current `permissions` table that affect what you'll see in the response.

Generated by reading `app/Services/SubscriptionPermissionService.php`, every `denyWithoutAppPermission(...)` call site under `app/Http/Controllers/Api/V1/*`, and the live contents of the `permissions` table. Verify against those sources if this drifts from the DB — this is not a generated/auto-synced doc.

## 1. The endpoint

```
GET /api/v1/app/permissions
Auth: Bearer <token> (guard: library_api), header: api_key
```

**Response**

```json
{
  "status": true,
  "data": {
    "welcome-banner": true,
    "book-seat": true,
    "add-branch": false,
    "...": "... one boolean per permission row, see below"
  }
}
```

If unauthenticated: `{ "status": false, "message": "Unauthenticated.", "data": {} }` (HTTP 200, not 401 — check `status`, not the HTTP code).

`data` always contains **every** permission row where `guard_name = 'library'** as a key — not just the ones the current user has. A missing key never happens; a key you don't recognize just means a permission was added to the DB after this doc was written — re-check `permissions` table.

## 2. Who can call it, and how the boolean is decided

The same endpoint serves two different account types, both authenticating through the `library_api` guard:

- **Library owner** (`Library` model): gets `true` for every permission included in their subscription plan (`subscription_permission` table, keyed by `library_type`). No per-owner override.
- **Library staff** (`LibraryUser` model, sub-accounts created under a library): gets `true` only for permissions that are **both** in the library's subscription plan **and** individually assigned to that staff member via `POST /api/v1/library/user/permissions/update`. A staff member can never have a permission the owner's plan doesn't include, no matter what's assigned to them.

So the same key can be `true` for the owner and `false` for one of their staff members — always read this per-logged-in-user, never cache it across accounts.

## 3. Two classes of permission — this is the part that matters most

Every key in the response *looks* the same (a boolean), but the backend treats them very differently:

- **Server-enforced**: a specific `Api/V1` controller action calls `denyWithoutAppPermission(...)` and returns HTTP 403 `{status:false, message:"You do not have permission to perform this action."}` if the permission is missing. For these, the permissions map is just a hint to pre-emptively hide the button — the server is the real gate.
- **Display-only**: nothing in `Api/V1` checks it. The backend will happily return data / perform the action regardless of this flag. **You are the only enforcement point** — if you don't hide the corresponding UI element yourself, there is nothing stopping the user from using that feature even though their plan/role says they shouldn't have it.

Section 5 marks every permission as one or the other, with exact endpoints for the enforced ones.

## 4. Known data issues (read this before wiring up flags)

These come from the `permissions` table's `slug` column, verified by replaying the exact backend logic (`orderBy('name')->mapWithKeys(...)`) against the live data. They are real, present-day bugs/quirks, not hypotheticals.

### 4.1 Eight slug collisions — one flag secretly represents two different permissions

`SubscriptionPermissionService::permissionStatusMap()` builds the response by keying a PHP array by slug. Where two permission rows share the same slug, the later one (alphabetically, by `name`) silently overwrites the earlier one — **you only ever receive one boolean, and it is not the one you'd guess from the "Menu Permission" name**:

| Response key you see | Rows that share it | Value you actually get reflects |
|---|---|---|
| `add-branch` | "Add Branch" (menu) *and* "Add Branch Master" (master data) | **Add Branch Master** |
| `add-floor` | "Add Floor" *and* "Add Floor Master" | **Add Floor Master** |
| `add-plan` | "Add Plan" *and* "Add Plan Master" | **Add Plan Master** |
| `add-plan-type` | "Add Plan Type" *and* "Add Plan Type Master" | **Add Plan Type Master** |
| `add-plan-price` | "Add Plan Price" *and* "Add Plan Price Master" | **Add Plan Price Master** |
| `add-expense` | "Add Expense" *and* "Add Expense Master" | **Add Expense Master** |
| `add-exam` | "Add Exam" *and* "Add Exam Master" | **Add Exam Master** |
| `download-payment-receipt` | "Download Payment Receipt" *and* "Download Receipt" | **Download Receipt** |

Practically: if you're gating a sidebar/menu item whose intent is "Add Branch" (the plain menu permission), the flag you read (`add-branch`) is actually driven by the unrelated "Add Branch Master" row. The two rows can be assigned independently to a staff member in the permissions UI, but only one of them is observable through this endpoint. Flag this to backend if you need the menu-level ones to be independently readable — they currently aren't.

### 4.2 Two soft-deleted permissions are still returned

`permissionStatusMap()` queries via `DB::table('permissions')`, which is a raw query builder call — Eloquent's soft-delete filtering (`deleted_at`) does **not** apply. Two rows that were soft-deleted on 2025-11-11 still show up:

- `attendence-report` (note the typo — "Attendence Report") — superseded by the correctly-spelled `attendance-report`.
- `activity-report` (the category-6 "Activity Report" row) — there's also `library-activity-report`, a separate, non-deleted permission.

Don't build UI around `attendence-report` (the misspelled one) — treat it as dead. Use `attendance-report` instead.

### 4.3 A few keys are not proper slugs — match them exactly, including case/spaces

Most keys are clean kebab-case, but these are stored verbatim in the DB and are **not** normalized:

| Permission name | Literal response key |
|---|---|
| Library Register | `Library-history` (capital L — case-sensitive!) |
| Library Enquiry | `library enquiry` (space, not hyphen) |
| Library Corner | `library corner` (space) |
| Video Training | `video training` (space) |
| Learner Feedback | `learner feedback` (space) |
| Book Category | `book category` (space) |
| Show / Hide Options | `show-/-hide-options` (contains a slash) |
| Add Locker Amount | `add-locker-amount-` (trailing hyphen) |
| Mark Attendance | `attendance` (not `mark-attendance` — collides in meaning, though not in key, with the "Manage Attendence" menu wording; there's no actual second `attendance` row, so no data collision, just a surprising name→key mapping) |

### 4.4 Two operations can be triggered *without* going through the permission check

`Api/V1/LearnerController` has two "shortcut" endpoints that bypass the generic, permission-checked `/library/learners/operation` endpoint entirely and perform the action directly, with **no `denyWithoutAppPermission` call at all**:

- `POST /api/v1/library/learners/swap-seat` (`swapSeat()`) — the "Swap Seat" permission is enforced only if you route the swap through `POST /library/learners/operation` with `operation: swap_seat`. Calling `/swap-seat` directly performs the swap for any authenticated library user/staff regardless of the `swap-seat` flag.
- `POST /api/v1/library/learners/gift-days/assign` (`assignGiftDays()`) — same story for "Gift Days"; only enforced via `/operation` with `operation: gift_days`.

If your app calls these dedicated endpoints directly (which is the more natural integration than going through the generic `/operation` action), you must enforce `swap-seat` / `gift-days` client-side yourself — the server won't. Worth raising with backend as a gap if strict enforcement matters for your use case.

## 7. Backend-side gap worth flagging

`MasterController::toggleFeatureList` / `updateToggleFeature` (the `/library/toggle-features/*` endpoints) require a permission literally named **"Manage Feature Toggles"** — but no row with that name exists anywhere in the current `permissions` table. Since `SubscriptionPermissionService::has()` can never find a match for a non-existent permission name, these two endpoints will return 403 for every single library account until a `permissions` row named "Manage Feature Toggles" is created and assigned to at least one subscription plan. Confirm with backend whether this is intentional (feature not yet released) before building against it.
